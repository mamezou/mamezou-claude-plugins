# 仕上げの別のモデルのレビュー

書いた本体と、同じモデルのサブエージェントは、同じ見落としをする。仕上げに、別のモデルで動く CLI に構成を読ませる。対象は、依頼者に見せる前の長い資料とする。数行の文面には使わない。

## 行う前に確認すること

- 資料を外部のサービスに送ることになる。顧客の資料、未公開の設計の情報、秘密の値、個人の情報のどれかを含む資料は、その案件で外部の CLI に送ってよいと依頼者が決めているときだけ送る。決まっていなければ、送る前に依頼者に聞く
- CLI に読ませる範囲は、対象の資料と、依頼文に書いた正本に限る。ほかのファイルを読ませない
- CLI が入ったマシンで実行する。クラウドのセッションからは、依頼者のマシンのセッションに実行を頼む
- 外部の CLI を使った事実を、先方に出す資料にどう書くかは、利用側の決まりに従う
- レビューは、本体と違うモデルで動いたときだけ「別のモデルのレビュー」と報告する。CLI の出力か設定からモデルの名前を読み、報告に書く。モデルの名前を読めなかったときは、読めなかったと書く

## 依頼文

依頼文はファイルに書き、同じ文を渡す。本体の見立てと、直したい箇所は書かない。`<...>` は資料の内容で置き換える。「確認すること」の1は、資料の種類に合う行だけを残す。

```text
次の資料の構成をレビューしてください。ファイルは編集しないでください。コマンドでファイルを作成、変更、削除しないでください。読むのは、対象と母集団の正本だけにしてください。

対象: <資料のパス>
資料の種類: <判断を求める資料 / 設計の記録 / 手順書 / 説明の資料>
読み手: <誰が読むか。読む前に知っていること>
読んだ後にすること: <決めること、行うこと>
母集団の正本: <パス。無ければ「なし」>
この資料の決まり: 冒頭の一覧に、本文の章と同じ数値と推奨を書くのは、決まりどおりで、重なりに数えない。スライドのときは、最初と最後の全体図と、部分のページの現在地を示す縮小が同じ中身であるのも、決まりどおりで、重なりに数えない。最後の全体図は、末尾のまとめとして数えない。

確認すること:
1. 題、見出し、各章の1文目だけを読んで、次のことを言えるか。
   判断を求める資料: 何を決める資料で、推奨が何か
   手順書: 何の作業を、どの順で行うか
   設計の記録: 何の、どの範囲の記録か
   説明の資料: どの問いに、どう答えているか
2. 冒頭の一覧の各項目に、呼び名の語を題に含む章が1つずつ、同じ順であるか
3. 同じ事柄と同じ数値が、冒頭の一覧を除いて2つ以上の章に書かれていないか。箇所を全部挙げる
4. 母集団の正本にあって、資料に出ていない項目
5. 1つの章に、種類の違う中身が入っていないか
6. 読み手の判断か作業を変えない章、節、表、列

返すもの: 1件ずつ、行番号、原文、問題、読み手への影響、重要度。直した文は書かない。
全体の合否と「出してよい」の判定は書かない。
```

## 実行

レビューごとに、新しい作業用のフォルダーを作り、依頼文と出力を置く。前のレビューの出力を上書きしない。

```bash
work=$(mktemp -d /tmp/doc-structure-review.XXXXXX)
# 依頼文を "$work/prompt.txt" に書く
```

Codex CLI

```bash
codex exec -s read-only -o "$work/review-codex.md" "$(cat "$work/prompt.txt")" < /dev/null 2> "$work/review-codex.log"
```

- `-s read-only` で、ファイルを変更できない状態で実行する
- `< /dev/null` を付ける。付けないと、入力を待って止まる
- `-o` で、最後の応答だけをファイルに保存する。モデルの名前は、実行の記録の `model:` の行にある
- git のリポジトリの外のフォルダーを読ませるときは、`--skip-git-repo-check` と `-C <フォルダー>` を足す

Devin CLI

```bash
devin -p --permission-mode auto --prompt-file "$work/prompt.txt" < /dev/null > "$work/review-devin.md" 2> "$work/review-devin.err"
```

- `-p` で、対話なしで実行する
- `--permission-mode auto` は、確認の要る操作を対話なしでは拒否する。ただし、利用者の設定で許可してある操作は確認なしで実行されるため、この指定だけでは書き込みを止められない。実行の後に、下の「変更が無いことの確認」を必ず行う。`--permission-mode dangerous` は使わない
- Devin が信頼済みにしてあるフォルダーで実行する。信頼していないフォルダーでは、対話なしの実行は「Refusing to run in an untrusted workspace」で失敗する。信頼の登録は、依頼者がそのフォルダーで `devin` を対話で起動して行う
- 最後の応答だけを保存する指定は無いため、標準出力をファイルに書く
- この手順での Devin のレビューは、まだ1回も最後まで通っていない。試した3回は、信頼していないフォルダーでの失敗が1回、確認の要る操作を拒否された後に応答が空で終わる失敗が1回、道具をファイルの読み取りに限る依頼文でファイルを読んだ後に応答が空で終わる失敗が1回だった

## 変更が無いことの確認

CLI の実行の後に、対象の資料とリポジトリが変わっていないことを確認する。

```bash
git -C <資料のあるリポジトリ> status -s
find <資料のフォルダー> -newer "$work/prompt.txt" -type f
```

変更があったときは、変更を戻さずに、変更されたファイルの名前を依頼者に伝える。

## 指摘の扱い

- 指摘を1件ずつ現物で確認し、採るか採らないかと理由を決める。指摘をそのまま信じない
- 2つの CLI の両方が挙げた指摘は、先に直す
- 載せる中身を足す指摘と、依頼者が決めた範囲を変える指摘は、本体の判断で採らず、依頼者に聞く
- 完了時に、実行した CLI とモデルの名前、採った件数、採らなかった件数と主な理由を依頼者に伝える

## 失敗したとき

- 1つの CLI のレビューが最後まで通れば、仕上げのレビューは行ったものとする
- CLI が失敗したときは、同じコマンドを繰り返さない。失敗の文を読み、依頼文かフォルダーの誤りなら直して1回だけやり直す。権限を広げてやり直さない
- 全部の CLI が失敗したとき、CLI が無いとき、送ってよい資料か決まっていないときは、レビューを行わずに進め、行っていないことと理由を依頼者に伝える
