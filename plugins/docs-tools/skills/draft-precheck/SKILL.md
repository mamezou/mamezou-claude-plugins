# 送付前チェック

引数で渡されたファイルを、同梱スクリプトで grep し、出現箇所を1件ずつ判定する。
引数の全体を1つのパスとして扱うので、空白を含むパスも引用符なしで渡せる。
直す対象が残っていなければ送付に進める。直す対象は本文の書き換えか別資料への切り出しで
除去する。

報告の規則: 依頼者への報告には、直した項目とその内容だけを書く。検出の一覧・バイト数などの
機械的な数値・通過の報告は書かない。直す対象がなければ、チェックには触れず本題だけ報告する。
例外は、後の「コードの出どころ」で求める報告で、該当する行があれば必ず書く。

## grep の実行

対象のパスは、下の枠の中の文字列の全体である。空白を含んでも1つのパスとして扱い、入力に
付いていた両端の引用符は外す。

```text
$ARGUMENTS
```

Bash で次の形のコマンドを実行する。パスは単一引用符で囲む。二重引用符で囲む形と、引用符なしの
形は使わない (パスの中の `$`・バッククォート・`"`・`\` をシェルが解釈するため)。パスの中に
単一引用符があるときは、その1字を `'\''` と書く。

```bash
${CLAUDE_SKILL_DIR}/scripts/precheck.sh '<対象のパス>'
```

枠が空のときと、スクリプトが「対象ファイルが見つかりません」を返したときは、パスを推測で
分けたり直したりせず、依頼者へ対象のファイルを確かめる。

## 出現箇所の判定基準

スクリプトの出力を項目ごとに次の基準で判定する。

- 内部パス断片・絶対パス・ローカル拡張子の素出し: すべて直す。本文を書き換えるか、資料を
  別に置いて参照する
- 文脈依存度の高い英単語: 文脈の説明を入れるか、日本語に置き換える
- 組版記号: 普通の表記 (「第 2 章」「2-5」) に置き換える
- 外部 AI 言及: 「内部レビュー反映」「クロスレビュー反映」の中立表現に置き換える
- 指示語: 指す対象の名詞に置き換えて読み、意味が変わらなければ名詞へ置き換える。残してよいのは、
  同じ文の中の直前語を受ける場合、名詞1語に置き換えると指す範囲が狭まる・ずれる場合
  (前の文や段落が述べた出来事・状況の全体を指すとき)、名詞へ置き換えると同じ名詞で始まる文が
  続く場合の3つ。同じ名詞で始まる文が続く場合は、前の文とまとめて1文にしてもよい。
  目安は1通あたり2回以下。「そのまま」「そのため」等の熟語は対象外
- 括弧の中身: 言い訳・根拠・属性の注記 (「(見積もり上の必須項目)」「(担当者名)」の類) は本文へ
  書き直すか削る。条件・状態を短く限定する機能的な括弧は残す
- 同じ括弧の中身が3回以上 (全角と半角の括弧は同じものとして数え、表の行も数える): 呼び名に
  括弧を付けて繰り返している場合 (「総務部(受付窓口)」の類) は、初出の表記へそろえて括弧を外す。
  表のセルで属性を括弧に入れている場合は、列を分ける。正式名称・略称の定義・画面の項目名の
  括弧と、条件・状態を短く限定する括弧は残す
- 3回以上の長い識別子: 初出だけフル表記にし、以後は呼び名にするか添付へ移す
- 読点が2つ以上の文 (括弧の中の読点は数えない): 書き直しを強制する項目ではない。該当の文を読み、
  読みにくい文だけ直す。条件・担当・複数の動作を1文に入れた文は、並ぶ項目を箇条書きへ出すか、
  動作の切れ目で文を分ける。理由と動作の2つだけの文と、同じ主語の動作をまとめた文は分けず、
  主題の直後の読点を外す。名詞を並べる読点だけの文は残す
- 60字超の文: 分けるか削る。分けた結果、理由と動作が別の文になる場合や、同じ形の短い文が
  並ぶ場合は分けず、修飾を削るか、1文のまま残す。括弧内の正式名称を除くと60字に収まる文と、
  表の行・コードブロックは対象外 (スクリプトは、行頭が `|` の表の行とコードブロックを数えない)
- 予告の文 (「次のとおり。」「次の〜がある。」「以下に示す。」などで終わる文): 直後の表・リストの
  題を言い直すだけの文は削る。残すのは、読者がする動作を述べる文か、表・リストを読む前に要る
  条件を述べる文
- 同じ文末が3文以上続く箇所 (「。」の前の2字が同じ文の並び)・「〜は、」で始まる文が3文以上続く
  箇所: 文末や書き出しの語だけを替えて済ませない。段落を読み直し、理由と動作を1文にまとめるか、
  用語の説明をリストへ出して書き直す。手順の並びのように、形をそろえて読ませる箇所は残す
- 物や事柄を主語にしがちな文末 (「発生する。」「決まる。」「変わる。」と、その否定・丁寧の形):
  先に、人の操作を述べる文か、仕組みを説明する文かを分ける。人の操作の文で、操作する人が
  その文か前後の文、または根拠の資料から分かるときは、人を主語にして動作を書く。仕組みの
  説明の文には人を足さず、何がいつどうなるかが分かる形へ直す。意味が取れている文は残す
- 未確認の印 (未確認 / 要確認 / TBD / 未定 / 要判断): 出典 (設計書・手順書・依頼者の発言・議事録)
  で確定できるなら確定して印を消す。確定できないなら、事実・背景・判断者・推奨・未確定でも
  進められる範囲を添えて報告の確認点にする。印だけを残した送付・報告はしない
- バイト数: 目安は、質問1点への回答が1000バイト未満、依頼・一覧を含む文面が1500〜2500バイト。
  超えるなら削る箇所を決める
- 誤検出の可能性がある箇所は、直す対象とは別枠で列挙し、判断を依頼者へ渡す

60字超の文・予告の文・同じ形の文の連続・物や事柄を主語にしがちな文末で検知された文は、
後の「直す手順」と「自然な文の見本」に従って直す。スクリプトは行を単位に文を数えるので、
文の途中で改行した文書では検知が漏れる。漏れは下の通し読みで拾う。

案件固有の禁止語と造語は、harness-ja プラグインを併用している場合は `.claude/harness.json` の
`draftPrecheck.bannedTerms` と Output Style「Concise JA」の避ける言葉の表で検査する。単体で
使う場合は、普通の日本語で言い換えられる語を言い換える。

### 主語と述語の対応 (必須。docs-tools:doc-review へ委任)

grep では検知できないため、エージェント `docs-tools:doc-review` に次の依頼を出し、返った指摘を
本体が現物で確かめて直す。

依頼文の要点: 対象ファイル / 見出し・表・コードブロックは対象外 / 各文の主語と述語を
抜き出す / 列挙する文の種類 (主語と述語が意味的に対応しない、主語が省略され直前の文
からも補えない、主語が2つで対応が曖昧、目的語が欠ける、3つ以上の論点を1文につなぐ) /
理由と動作の2つを1文で書いた文 (「〜ため、〜する」) は列挙しない / 出力は行番号・原文・
抜き出し・種類・言い換え案1つ / 判断に迷う文は「判断保留」として分ける / 修正はしない。

応答に書くのは、直した文の変更前後だけ。件数・通過の報告は書かない。

### 読者としての通し読み (必須。docs-tools:doc-review へ委任)

機械チェックと主語と述語の確認の通過を品質確認としない。検知された形を1文ずつ直した文章は、
検査を全て通っても、同じ形の短い文が並んで読みにくいことがある。書いた本人は内容を知って
いるので、読者がつかえる箇所を見落とす。エージェント `docs-tools:doc-review` に読者として
読ませ、返った指摘を本体が現物で確かめて直す。主語と述語の対応の依頼と1つにまとめてもよい。
まとめるときも、通し読みの指摘は主語と述語の指摘と分けて返させる。

依頼文の要点: 対象ファイル / 読者を名指しする (例: 設定作業を行う先方の担当者。対象の仕組みは
知らない) / 読者として頭から最後まで通して読む / つかえた箇所を行番号・原文・理由・直し案1つで
返す / 下の5種は必ず見る。5種以外でも、読んでつかえた箇所は挙げる / 節ごとに「読者が読んだ
後に何をするか」を1文で書き、書けない節を挙げる (節のない短い文面は全体で1文) / 下の4点を
判定し、問題のある点だけを同じ形で返す / 修正はしない。

必ず見る5種:

- 人の動作が見えない文 (物や事柄が主語で、誰が何をするかが分からない)
- 情報のない予告の文 (表やリストの前で「次のとおり」とだけ述べる)
- 同じ形の文が3文以上続く箇所
- 用語の説明と本題が混ざった段落
- 主題の直後の読点で切れる短い文の連続 (「A は、〜する。B は、〜する。」)

判定する点 (相手の質問・依頼の原文があれば、依頼文に転記する):

- 経緯・結論が、依頼・詳細より先に書かれているか
- 隣り合う節に矛盾して見える並びがないか (例: 報告と依頼の食い違い)
- 読み手がそのまま実行・判断できるか (不足している情報がないか)
- 本文の各段落が、引用した質問か依頼のどれに対応するかを言えるか。言えない段落は
  削除候補 (背景説明・質問にない論点への先回り・読み手が知る経緯の再掲・未確定の
  作業予定)

応答に書くのは、直した文と段落の変更前後だけ。件数・通過の報告は書かない。

### 依頼との照合 (短い文面を含む全チャネル。依頼者の指示があるとき。docs-tools:doc-review へ委任)

通し読みは、文面の読みやすさを見る。依頼者が指示した内容が文面に入っているかは、見ない。
言い方だけを直す指摘のあとに、事実・依頼・約束が増えたり減ったりしても、検査を通ってしまう。
依頼者の指示と文面を比べて、足した内容と消した内容を拾う。

依頼文の要点: 依頼者の指示の原文 (または、書く前に「必ず入れる」「入れない」「未確認」に分けた
一覧) / 対象の文面 / 返すもの: 指示にあって文面にない内容 (欠落) / 文面にあって指示にない内容
(追加。事実・数・日付・約束・依頼・理由を、種類ごとに) / 指示と文面で断定の強さが違う文
(「予定です」と「します」など) / 実例から持ち込んだ事実の疑いがある文 / 修正はしない。
1 件ずつ、指示の原文と文面の原文を並べさせる。返信の文面では、返信元のメールの全文も渡し、
相手の話題に答えていない箇所と、返信元にない事実を述べた箇所も返させる。

本体は、返った指摘を現物で確かめる。追加は削り、欠落は足し、強さは指示に合わせる。依頼者が
前の版で承認した内容は、指示に書かれていなくても残す。判断に迷う足し引きは、本体の判断で
行わず、依頼者へ聞く。言い方の指摘を受けて直したときは、変更前後を並べ、内容に差がないことを
応答に書く。

### 元の資料との照らし合わせ (元の資料がある設計書・手順書・共有ページと、事実を述べる送付文面。docs-tools:doc-review へ委任)

通し読みは、資料に書いてあることしか見ない。元の資料にあった項目が抜けていても、元の資料と違う
事実が書かれていても、通し読みでは分からない。先方へ送った文面・旧版・作業の記録など、資料の元に
なった資料があるときは、エージェント `docs-tools:doc-review` に元の資料と照らし合わせさせ、返った
指摘を本体が現物で確かめる。

事実・数・時刻・コマンド・判断を述べる送付文面では、設計メモ (`/docs-tools:send-draft` の「設計メモ」)
の「使う事実」の欄に書いた出典を、元の資料として渡す。設計メモは、下の「渡すもの」で渡さないとした
本体の要約にあたるため渡さない。出典がファイルでないとき (依頼者の発言、依頼者が会話に貼った結果) は、
設計メモに引用した原文を、言い換えずに渡す。送付文面では、答えさせることの 2 つ目 (元の資料にあって
資料にない項目) は返させない。文面に載せる中身は、設計メモで依頼者と決めてある。

渡すもの: 対象ファイル / 読者 / 依頼の原文 (資料に何が求められているかを読ませる) / 元の資料の
パス (読む範囲を行で指定してよい) / 依頼者が載せないと決めた内容。資料を書くときに本体が作った
指示や要約と、本体の見立て (「不足はないはず」等) は渡さない。指示を渡すと、指示どおりかどうか
しか確かめられない。

答えさせること:

- 名指しした読者が、資料だけで作業を始められるか。手が止まる箇所を行番号・原文・理由で返す
- 元の資料にあって、資料にない項目 (作業、受け渡す情報、条件)。依頼者が載せないと決めた内容は除く
- 資料の記述のうち、元の資料と合わないもの (項目名、画面の名称、条件、担当)。資料と元の資料の
  両方を、行番号と原文で並べて返す。元の資料どうしが合わない箇所も挙げる
- 資料の記述のうち、元の資料に裏づけがないもの。表の行には、裏づけにした元の資料の行を添える
- 読んだ資料と、読んでいない資料

全体の合否や「出してよい」の判定は返させない。判定を返させると、本体が判定を出来の証拠にする。

指摘の扱い: 元の資料と合わない記述と、裏づけのない記述は、現物で確かめて直す。元の資料どうしが
合わないときは、片方に決めず、両方を引用して依頼者へ渡す。元の資料にあって資料にない項目と、
手が止まる箇所で挙がった不足は、依頼者が決めた載せる範囲に入るものだけ足す。範囲に入るかを
本体が決められないものは足さず、件数と主なものを依頼者へ伝える。

### コードの出どころ (コードブロックを含む送付文面のとき)

文面に載せたコマンドやクエリを誰かが実行したのか、Claude が書いただけなのかは、文面を読んでも
分からない。本体は同梱スクリプトで、コードブロックの各行が会話の記録のどこに出ていたかを表示する。
スクリプトは止めない (終了コードは常に 0)。

```bash
${CLAUDE_SKILL_DIR}/scripts/code-origin.sh '<対象のパス>' ['<会話の記録の JSONL>']
```

- 会話の記録を省くと、今のディレクトリの会話の記録の置き場 (`~/.claude/projects/` の下) から、
  最後に書かれた記録を使う。文面を別のセッションで作ったときは、文面を作ったセッションの記録を渡す。
  記録の場所は `/docs-tools:session-recall` の出力で分かる。どのセッションで作ったかが分からない
  ときは、依頼者に聞く
- スクリプトは各行の出どころを、依頼者の入力 / ツールの結果 (エラーを除く) / 成功したコマンド /
  Claude の応答 (ほかのツールへの入力を含む) に分けて出す
- 文面のファイル名を含むツールの呼び出し (文面の書き込み・読み込み・検査) と、呼び出しの結果は
  数えない。文面のファイル名を含む最初の呼び出しより後の記録には、「文面を作り始めた後」の印を付ける
- 各区分の記録には、同じコードブロックの何行を含むかを添える。1 語だけの行は検索の語など別の文脈でも
  出るため、本体は、ほかの行も含む記録を優先して読む。「文面を作り始めた後」の印の記録は、文面を
  写しただけの記録のことがあるため、記録の行を開いて確かめる
- スクリプトが「見つかりません」と出したときは、出どころを確かめられなかったことを報告に書く

判断と報告: 本体は、「どこにも出ていない行」「失敗したコマンドかエラーの結果にだけ出ている行」
「Claude の応答にだけ出ている行」を、次の 3 つに分ける。分けた結果は、行番号をまとめて依頼者への
報告に 1 行で書く (例: 「36〜40 行目は相手に実行をお願いするクエリ、42 行目は確かめていないコード」)。

- 相手に実行をお願いするコマンド: 設計メモか依頼者の指示に、相手に実行をお願いすると書いてあるもの
- 依頼者が実行したコード: Claude が示したコードを依頼者が実行し、結果だけを会話に貼ったときは、
  コードは Claude の応答にだけ出る。`/docs-tools:session-recall` の直後の記録の欄で、貼られた結果を
  確かめ、記録の場所を添える
- 確かめていないコード: 上の 2 つに当たらないもの。本文から外し、設計メモの「未確認」の欄へ移す

3 つのどれかを本体が決められない行は、決めずに依頼者に聞く。

### 長文資料の構造 (必須。設計書・手順書・共有ページのとき)

チャット文面より長い資料は、上の読者としての通し読みに加えて次の表で節ごとに判定する。
文単位の grep と主語述語の確認では、事実を並べただけの段落や 3 事項を入れたセルは
通ってしまうため、表で見る。`docs-tools:doc-review` へ依頼するときはこの表を依頼文に
転記する。

| 確認項目 | 判定 |
|---|---|
| 節の構造 | 方針 / 理由 / 手順 (または 事実 / 判断 / 次の一手) に分かれているか。事実の羅列だけの段落は不可 |
| 読者の行動 | 節を読んだ読者が何をするかを 1 語で言えるか (判断する・実行する・確認する)。言えない節は削除候補 |
| 表のセル | 1 セルは名詞句 1〜2 個まで。3 事項以上や説明文は行を分けるか本文へ移す |
| 経緯・日付 | 本文に確認日・作業経緯を書かない。書くなら記録の節に分ける |
| 結論の位置 | 1 章で「何を・なぜ・どの順で」が 5 行以内で読めるか |
| 背景・冒頭 | 資料が要る理由 (誰が何をする必要があるか) から始まっているか。機能や仕組みの説明から始まる背景は不可 |
| 図 | 3 つ以上の要素の関係や構成を、文と表だけで書いていないか。1 枚で示せる関係は図にする。手順は表で足りる |
| 手順の要素 (手順書のみ) | 各手順に 実施者 / アクセス手段 / コマンドか画面操作 / 完了条件 がそろっているか |

## 直す手順

検知された文を1つずつ直すと、同じ形の短い文が並びやすい。文の形の指摘 (スクリプトの検知と
通し読みの指摘) は、段落の流れを見て直す。

- 指摘された文を直したら、その文を含む段落を頭から読み直す。直した文だけを見て確定しない
- 文の形の指摘を局所の修正で直すと段落の流れを保てない場合は、文単位の修正をやめて段落を
  書き直す。目安は、同じ段落で2件以上直すことになったとき。段落を読んだ読者にしてほしい
  動作を先に決め、下の見本の形で書く
- 内容の指摘と、依頼者から受けた文言の指摘 (特定の語や言い回しへの指摘) は、段落の書き直しの
  対象にせず、従来どおり指摘された箇所だけを最小差分で直す
- 依頼者から書き方の指摘 (括弧が多い、読点が多い、文が長い等、ほかの箇所にも当てはまる指摘) を
  受けたら、指摘された文を直すだけで終えない。同じ種類の箇所をスクリプトで全文から数え、対象の
  一覧と直し方を、指摘された文の直しと同じ応答で示す。一覧の箇所を直すかどうかは、依頼者の返事と
  利用側の決まりに従う
- レビューの指摘で注意書きや説明を足すのは、読者が作業を進められない欠落に限る。足したら、
  足した分と同じだけ削る
- 指摘を反映した後の版には、読者としての通し読みをもう一度通す

## 自然な文の見本

検知された形を避けるだけでは、読みやすい文にならない。書き直すときは、下の「直した後」の形に寄せる。

人の操作を述べる文は、操作する人を主語にして動作を書く。主語にするのは、直す前の文か前後の文に
出ている人に限る:

- 直す前: 接続先の登録は、管理者がアプリを追加するたびに発生する。
- 直した後: 管理者はアプリを追加するたびに接続先を登録する。
- 直す前: アプリの公開範囲によって、担当者が割り当てるグループが変わる。
- 直した後: 担当者は、アプリの公開範囲に合わせて割り当てるグループを選ぶ。
- 直す前: セッションの保持時間は、開発者がアプリ側で行う設定で決まる。
- 直した後: 開発者はセッションの保持時間をアプリ側で設定する。

仕組みを説明する文は、人を足さずに、何がいつどうなるかを書く:

- 直す前: 接続先の登録は、アプリの追加ごとに発生する。
- 直した後: アプリを追加するたびに接続先の登録が必要になる。

表やリストの題は見出しに書き、題を言い直すだけの文は置かない:

- 直す前: 作業と担当は、次のとおり。
- 直した後: (文を削り、見出しの直後に表を置く)
- 直す前: グループの扱いには、次の制約がある。
- 直した後: (文を削り、見出しを「グループの制約」にして、直後にリストを置く)

理由と動作は、1文にまとめる:

- 直す前: 割り当ては、入れ子のグループへ及ばない。担当者は、利用者をグループの直接のメンバーにする。
- 直した後: 割り当ては入れ子のグループへ及ばないため、担当者は利用者をグループの直接のメンバーにする。

同じ主語の文はまとめ、主題の直後の読点は毎回は打たない:

- 直す前: 担当者は、申請の内容を確認する。担当者は、確認した申請を管理者へ回す。管理者は、申請に沿って設定を変更する。
- 直した後: 担当者は申請の内容を確認し、管理者へ回す。管理者は申請に沿って設定を変更する。

用語の説明は、本題の段落から出してリストにする:

直す前

```text
証明書は、認証基盤が応答に署名するためのファイルである。応答は、認証基盤がアプリへ返す
ログインの結果にあたる。証明書は、接続先ごとにある。証明書の期限が切れると、利用者の
ログインが失敗する。管理者は、証明書を期限が切れる前に更新する。
```

直した後

```text
証明書の期限が切れると利用者がログインできなくなるため、管理者は期限が切れる前に接続先ごとの
証明書を更新する。

- 証明書: 認証基盤が応答に署名するためのファイル
- 応答: 認証基盤がアプリへ返すログインの結果
```

先方へ出す資料は書き言葉で書く。話し言葉の言い回しを使わない:

- 直す前: 証明書の登録が要ります。
- 直した後: 証明書の登録が必要です。
- 直す前: 既定の証明書は使えません。
- 直した後: 既定の証明書は利用できません。

対象は名前で書く。「今回の」「今の」で指さない:

- 直す前: 本書は、今回の構成の要件に照らして 2 つの方式を比べたものです。
- 直した後: 本書では、検証環境と本番環境の入口に置くサービスとして、2 つの方式を比較します。

前の文への付け足しと、資料の中の場所を案内する文は削る:

- 直す前: 基本料は月額 5 万円です。ほかに、通信量に応じた料金がかかります。経緯は 2 章に書きました。
- 直した後: 基本料は月額 5 万円です。通信量に応じた料金は別にかかります。

例は、どの案件にも当てはまる形で書く。システム名・人数・工数を作って入れない:

- 直す前: 受発注システムのデータベースのパスワードを、ソースコードから保管の仕組みへ移す。工数は 1 人日です。
- 直した後: パスワードがソースコードにハードコーディングされていないか調査し、見つかった箇所を安全な保管場所へ移す。
