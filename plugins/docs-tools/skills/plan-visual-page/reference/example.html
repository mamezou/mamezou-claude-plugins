店舗データの送信経路 / 事前検証の計画

店舗の在庫データも中継サーバーを通るかを、11/24までに確かめる

期限 11/24(火) 使う端末 検証用の店舗端末2台 中継サーバー 本番と同じもの 新しい集計サーバー stg

前提: なぜこの検証をするのか

何のための作業か

  • 店舗のデータを集める集計サーバーを、新しいサーバーへ切り替える
  • 切り替えの後は、店舗端末からのデータをすべて中継サーバー経由で送る方式にする

今どうなっていて、何が困るか

  • 売上データは中継サーバーを通るが、在庫データは店舗端末から旧集計サーバーへ直接送られている
  • 在庫データの宛先を変えたときに、中継サーバーを通って新しい集計サーバーへ届くかは、まだ確かめていない
  • 届くかどうかで切り替えの手順が変わるため、確かめるまでは本番の日程を確定できない

そこで、本番の切り替えの前に、在庫データも中継サーバーを通るかを検証用の端末で確かめます。結果で切り替えの手順と日程を確定し、担当者Cへ連絡します。担当者Cには「事前検証の後に確定する」と伝えてあります。

確認していただきたいこと

  1. この計画で進めてよいか
  2. よければ、共有ページの「集計サーバーの切り替え」の下に起票します
  3. 起票の後に、手順1(店舗端末の設定と戻しの手順書づくり)を始めます

データの経路: なぜ今のままでは確かめられないか

今の店舗端末の設定 売上データだけが、中継サーバーを通る
端末店舗のレジ・在庫端末
中継サーバーrelay.example.com
集計サーバー旧
端末店舗のレジ・在庫端末
集計サーバーstock-old.example.com

在庫データは、中継サーバーを通らずに旧集計サーバーへ直接送られる

理由: 店舗端末の設定で、在庫データの宛先が stock-old.example.com に固定されているため。

検証用の設定 すべてのデータが中継サーバーを通る
端末検証用の店舗端末2台
中継サーバーrelay.example.com
集計サーバー新(stg)

変えるのは、検証用の店舗端末2台の設定1つと、中継サーバーの転送先1つだけ。在庫データの宛先を中継サーバーにし、中継サーバーの転送先に新しい集計サーバーの stg を足す。ほかの店舗端末は変えない。

中継サーバーは、受け取ったデータに店舗コードを付けて転送します。在庫データにも店舗コードが付くかを、今回の検証で合わせて確かめます。

作業の順番

先 中継サーバー側の準備 転送先と、受け付けるデータの種類を足す。今の店舗端末のまま、売上データが新しい集計サーバーにも届くかまで確かめる
→
後 店舗端末への反映 検証用の2台の設定を夜間に変え、検証の後に元へ戻す
  • 売上データはすでに中継サーバーを通るため、中継サーバーの設定が正しいかは今の店舗端末で確かめられる
  • 店舗端末を検証用の設定にしておく期間が短くなる

決まっていることと、店舗端末への影響

決まっていること(11/16)

  • 検証には、検証用の店舗端末2台だけを使う。営業中の店舗の端末は変えない
  • 中継サーバーの転送先には、新しい集計サーバーの stg をそのまま指定する
  • 中継サーバーの管理画面での作業は担当者A。操作の手順は Claude が書く
  • 店舗端末の管理者パスワードは、検証の当日に担当者Aが確かめる。Claude は値を見ない
  • 検証用の2台の利用は担当者Bの了承済み。条件は、設定の差分を見せることと、夜間に反映すること

店舗端末への影響

  • 11/17 の夜から戻すまでの間、検証用の2台の在庫データは旧集計サーバーに届かない
  • 反映は夜間だけ。理由は、担当者Bの「営業時間中に設定を変えると、レジの再起動で会計が止まる」という指摘
  • 期間中に店舗端末の一斉更新が入ると、検証用の設定は上書きされる
  • 旧集計サーバーの在庫の画面で、検証用の2台の数字が止まって見える可能性がある 未確認。検証の間は stg の画面で確かめる

中継サーバーで気をつけること

  • 転送先を足す前に、中継サーバーのディスクの空きを確かめる(転送が詰まると、受け取ったデータを一時的にためるため)
  • 検証の間は、中継サーバーから新しい集計サーバーへの送信 443 を止めない
  • 中継サーバーの設定の変更はサーバーの変更なので、手順書と GO が要る。転送先を元に戻すのは担当者A
