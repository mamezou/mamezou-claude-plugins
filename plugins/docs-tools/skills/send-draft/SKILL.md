# 送付ドラフトの作成

対象は Teams (先方向け) と Slack (内部向け) のチャット文面と、メール (先方・内部向け) の文面。
設計書・見積書クラスの長文資料は対象外。
ドラフトの置き場は利用側のリポジトリで決める (既定は `docs/drafts/`。型は置き場によらず共通)。

## 作成前に固定する

- 用途: 返信 / 依頼 / 相談 / 報告 / 共有案内 / 内部の軽い連絡 のどれか
- 宛先とチャネル (先方 = Teams またはメール、内部 = Slack またはメール)。宛先は指示にある人だけ。
  指示にない宛先・cc を足さない。宛先の人から別の相手へ渡してもらう文があるときは、
  その文を最後に読む相手も決める
- 実例の確認: 書く前に、依頼者が過去に送った同じ種類の文面を読む。メールは後の「メールの下書き」の
  手順 1 に従う。Teams と Slack は、依頼者の過去の投稿を同じ宛先で探して読む。見つからないときは、
  見つからなかったと応答に書き、このファイルの型を使う
- 依頼の仕分け: 今回の依頼の内容を「必ず入れる」「入れない」「未確認」に分けて応答内に示す。
  依頼者の指示にない事実・依頼・約束を、本文に足さない。依頼ごとに、担当、権限、依存する後続作業を
  確かめる。こちらで安全に実施でき、依頼者が分担を決めていないときは、文面の外で当方実施の案を
  示して判断を待つ。技術的に実行できることだけを理由に担当を移さない (チャネルによらない)
- 設計メモ: 後の「設計メモ」の節に従う。ドラフトファイルには送信本文だけを書き、設計メモ・
  内部メモ・前提情報は入れない
- 本文を書く前に、文面の設計 5 点を 5 行以内で依頼者へ示し、OK を得る:
  1. 宛先と通数 (実施依頼と判断相談は 1 通に混ぜない)
  2. 依頼か相談かの別
  3. 実施の分担 (先方作業と当方作業)
  4. 添付の形 (何を渡すか)
  5. 期待する返事 (実施の連絡か、可否の判断か、選択肢からの選択か)。
     選んでもらう相談を、可否の問いに変えない

## 設計メモ

相手の問いと、相手がすでに知っていることを確かめずに中身を決めると、ずれたまま書き直しが続く。
推測や実行していないコードを事実と同じ形で書くと、相手は確かめていないことを前提に動く。
設計メモは、本文を書く前に中身を依頼者と決めるための控えで、送らない。

- 対象: 事実・数・時刻・コマンド・判断を述べる文面。用途 (返信・依頼・相談・報告・共有案内) に
  よらない。事実も判断も述べない 1〜2 文の軽い連絡 (お礼・受け取りの連絡など) は対象外
- 置き場: 利用側で決める。既定は下書きと同じフォルダで、下書きのファイル名から拡張子を除いた名前に
  `.brief.md` を付ける (例: `slack-<宛先>-<件名>-YYYYMMDD-draft.brief.md`)
- 作り方: `${CLAUDE_SKILL_DIR}/templates/brief.md` を複製し、8 つの欄 (相手の問い・依頼 / 相手が
  すでに知っていること / 1 文目に書く答え / 使う事実と出典 / 未確認 / 依頼者が決めたこと /
  読み手と本文の用語 / 読み手の次の行動) を、型の `<...>` の説明に従って埋める
- 相手がすでに知っていること: 書き手は、最後に読む相手へこれまで送った文面とやり取りを読んで書く。
  相手にまだ伝わっていないことのうち、依頼にない事柄は本文に足さず、設計メモの「未確認」の欄に入れる
- 探す範囲: 書き手は、相手とのやり取り、作業ログ、根拠の資料に加えて、前のセッションの記録を
  `/docs-tools:session-recall` で探す
- 欄を推測で埋めない。探しても見つからない欄は「見つからない (探した場所: …)」と書き、設計メモを
  示すときに依頼者に聞く
- 文面に使えるのは、「使う事実」の欄に出典のある事実だけ。「未確認」の欄の事柄は本文に入れない
- 書き手は、埋めた設計メモを設計 5 点と合わせて依頼者に示し、返事を得てから本文を書く。依頼者が
  決めたことは、返事と指摘を受けるたびに「依頼者が決めたこと」の欄に足し、次の版はこの欄と
  照らしてから出す

## 指摘を受けたときの対応

- 指摘を「文言」か「設計 (宛先・通数・分担・構成・添付)」かに分類する
- 相手の問い・1 文目の答え・使う事実が変わる指摘は、先に設計メモを直して依頼者へ示し、返事を得てから
  全文を作り直す。事実が変わらず言い方だけを直す指摘は、次の文言の指摘として扱う
- 文言の指摘は最小差分で直す。事実・依頼・約束を足さず、消さない。直したら、変更前後を
  並べ、内容に差がないことを示す。内容を変える提案は、文面とは別に出し、指示を待つ
- 設計の指摘は、該当の設計 5 点を直したうえで全文を作り直す。一部の文だけを差し替え
  ない (一部だけの差し替えは別の矛盾を生む)。作り直したら、受けた指摘の一覧と
  突き合わせてから出す

## メールの下書き

メールは、ファイルに書いた本文を、メールのツール (Gmail の MCP ツールなど) の下書き作成へ渡して
作る。次の順に進める。

1. 実例を読む: 送信済みのメールを検索し、本文を取得して読む。同じ宛先の 1 件と、別の宛先の
   2 件以上を目安にする。検索の結果は一覧だけで本文を返さないことが多いので、本文は取得の
   ツールで読む。添付ファイルは読まない。読んだ実例は、宛先と日付を応答に挙げる
   返信の下書きでは、実例に加えて、返信元のスレッドを取得して全文を読む。相手の話題に答える
   文を、依頼文だけから推測して書かない
2. 実例から取るもの: 宛名・あいさつ・段落・見出し・箇条書き・結び・署名の型と、言い回し。
   事実・数・日付・約束は、今回の依頼と根拠資料から取り、実例から持ち込まない。実例に
   古い約束や誤りがあっても、写さない
3. 設計 5 点と、設計メモ (「設計メモ」の対象の文面のとき) と、依頼の仕分け (必ず入れる / 入れない /
   未確認) を依頼者へ示し、OK を得る。
   宛先 (To・CC) と件名もここで示す。CC は、依頼に明記された人だけを入れる
4. 本文を `docs/drafts/` に書き、`/docs-tools:draft-precheck` を通す。依頼との照合 (追加・欠落・
   強さの変更) も通す。返信では、返信元のメールも照合の対象に渡す
5. 検査を通した本文を、書き換えずに、下書き作成のツールへ渡す。本文は、プレーンテキストの
   `body` で渡す。HTML の引数だけで渡すと、hook の検査を通らない。返信は、返信先のメッセージを
   指定して下書きを作る。この Skill は下書きを作るまでで、送信するツールと、即時に返信する
   ツールは使わない
6. 下書きを作った後、宛先・CC・件名・本文を応答で示す。送信は依頼者が行う

## 置き場と命名

- `docs/drafts/<チャネル>-<宛先>-<件名>-YYYYMMDD-draft.txt`
- 拡張子は .txt、中身は送信本文のみ
- 送付が確認できたら即 `archive/sent/` へ移動する (移動は送付確認後の別作業)

## 用途別の型とひな形

Teams の依頼・返信は `templates/` のひな形の複製から作る。構成を新規に作文しない。

- 依頼: `templates/teams-request.txt`。用件 1 文 (何を頼むか) → 前提となる完了済みの事実 (要るときだけ
  1 文) → 「■ 項目名」+「・ラベル: 値」の一覧 → 返してほしい物と送る物 → 締め
- 相談 (可否の判断を求める): `templates/teams-consult.txt`。相談の 1 文 →
  現状と理由 → 変更後も残る安全の仕組み → 了承時の作業 (添付・元・変更) →
  了承が難しい場合の代わりの案
- 相談 (選択肢から選んでもらう): 決めてほしいことを 1 文 → 選択肢ごとに、実際の値、
  選んだ結果、相手の作業。勧める選択肢は、その行に理由を添えて 1 回だけ書く。
  末尾に可否の問いを足さない
- 返信 (質問への回答): `templates/teams-reply.txt`。「＞ 質問文」で引用 → 直後に
  「結論: 〜」 → 理由。質問が複数ならこの組を繰り返す
- 共有案内: `templates/share.txt`。共有物の名前と場所 → 資料名+1行説明 →
  見てほしい点 → 依頼 (確認・返答)
- 報告 (実施の連絡、Slack 内部向け): `templates/report.txt`。結論 1 文 → 実施内容 → 確認結果 →
  次の作業。依頼・お伺いを混ぜない
- 内部の軽い連絡 (訂正・お礼・FYI): `templates/slack-note.txt`。1〜2 文の単発
- メールの新規: `templates/email-new.txt`。用件の 1 文 → 話題ごとの「■」見出しと本文 →
  日程や項目の「・」の箇条書き → 結び。宛名・あいさつ・結び・署名は実例から取る
- メールの返信: `templates/email-reply.txt`。相手のメールを受ける 1 文 → 相手の話題ごとの
  「■」見出しと回答 → 結び
- 依頼者宛のチャット報告は本 Skill の対象外
- 行数・箇条書きは実例からの目安。必要な情報が少なければ、行や項目を増やさない

依頼ひな形の記入規則:

- 項目行は「ラベル: 値」のみ。理由・注意・説明の文を入れない。理由は設計資料側に
  置き、必要なら参照 1 文で案内する
- 期限・催促を書かない。書くのは依頼者が期限を指定した場合のみ
- 「別途」「準備でき次第」等の後送を書く前に、今渡せないかを確認する。渡せる物は
  添付・記載で今回の依頼に含める
- 値・設定指示の各行は出典 (実環境コマンド・実装コード・設計書) を設計メモの「使う事実」に
  書く。設計書のみが出典の値は、実装・実環境との照合まで行う

## チャネル別の型

Teams (先方向け):

- 新規の Teams の投稿で件名の欄を使えるときは、1 行目に件名を書く。既存のスレッドへの返信では件名を足さない。件名の形は同じ用途の送付版に合わせる
- 宛名「〇〇 様」。cc があれば下の行に「cc 〇〇 さん」
- 挨拶「お世話になっております。<会社名>の<氏名>です。」、締め「よろしくお願いいたします。」
- 感嘆符は使わない。長文の区切りは「■」見出し (Markdown の # は使わない)
- コードブロックは使わず、ファイル名・値は地の文か箇条書きに書く

Slack (内部向け):

- 宛名・挨拶は書かない。必要なときだけ先頭にメンション。締めの有無と文言は、利用側の「実例の確認」に従う。同じ宛先・用途の実例がなければ、同じチャネル・用途の実例 2 件に合わせる。型を決められない場合は締めを書かない
- 本文から直接始める
- 用意した物の共有は、何についての何を用意したかを 1 文で書き、リンクを付ける。
  相手が分かっている作業を、依頼の文として足さない
- 依頼は言い切る (「〜をお願いします」「〜をお願いしたいです」)。可否を尋ねる形
  (「〜をお願いできますか」) にしない。相手の了承を得てから自分が動く相談は、問いの形で書いてよい

メール:

- 宛名・あいさつ・段落・見出し・箇条書き・結び・署名は、読んだ実例の型に合わせる。
  実例がない宛先のときだけ、次の既定を使う
- 既定: 宛名は会社名の行と「〇〇 様」の行。cc が依頼に明記されているときだけ、「(CC：〇〇 様)」を
  同じ行に添える。
  あいさつは「お世話になっております。」と「<会社名>の<氏名>です。」の 2 行。締めは
  「引き続きどうぞよろしくお願いいたします。」。署名は会社名と氏名の 2 行
- 1 文を 1 行にし、話題ごとに空行で分ける。複数の話題は「■」見出しで分ける。日程や項目は
  「・」の箇条書きにする
- 感嘆符は使わない。Markdown の記法は使わない

## 長さの目安

- 質問 1 点への回答: 1000 バイト未満
- 依頼・一覧を含む文面: 1500〜2500 バイト
- 相手が既に知っていること (設計メモの「相手がすでに知っていること」) を説明しない

## 構成と通し読み

- 構成の順序: 1 文目に用件 (何の件か、何を用意したか、何を頼むか) を書く。依頼・相談は、用件 (何を
  頼むか) → 判断の材料 (選択肢・理由) → 当方で実施する事項 → 締め の順にする。報告は、結果 → 根拠 →
  次の動き の順にする。経緯は、判断の材料として要る分だけ、用件の後に書く
- 識別子・設定差分などの詳細は本文に並べず、添付ファイルへ置く。本文は変更の
  趣旨と理由に絞る
- 長い英字の識別子は初出のみフル表記し、以後は呼び名で書く (同一識別子 3 回以上は
  harness-ja の hook が差し戻す)
- 書き終えたら、送付相手の目で頭から読む通し読みを `docs-tools:doc-review` へ依頼する。
  機械チェックの通過を品質確認としない。依頼は `/docs-tools:draft-precheck` の必須項目として行う

## 送付前チェック (必須)

Write 後に `/docs-tools:draft-precheck` を対象ファイルへ実行する。hook(プラグイン harness-ja の
`draft-precheck.sh`)が検査するのは編集差分の禁止語・内部表現のみで、指示語の件別判定と主語述語の確認は
`/docs-tools:draft-precheck` にしかない。省略しない。全てのヒットを判定し、直す対象が残って
いないことを確かめてから依頼者へ提示する。送付は依頼者が行う。`/docs-tools:codex-review` は依頼者が指示した
ときだけ行う。

メールのツールへ渡す本文は、harness-ja の `draftPrecheck.toolRules` に当該のツールを書くと、渡す
ときにも hook が同じ検査をする。書いていない案件では、hook は何もしないため、この Skill の
手順 4 の検査を省かない。

## 指摘を受けた 2 回目以降

- 直す範囲は指摘された箇所に限る。形 (文章 / 箇条書き) と分量は、指示がない限り変えない。
  指摘と反対側の極端 (長すぎ→短すぎ等) に直さない
- 依頼が入れる内容を決めていない (「調整して」「作って」で項目の指定がない) ときは、
  推測で選ばず、書く前に入れる項目・入れない項目・形・分量を 1 回で確認する。
  新規・調整とも同じ。機械検知はなく、判断で防ぐ
- 修正版も毎回 `/docs-tools:draft-precheck` を通す (1 文 60 字の検知を含む)。Slack 文面も対象

## 関連

- 用語の言い換えは、harness-ja プラグインを併用している場合は Output Style「Concise JA」の避ける言葉の表に
  従う。単体で使う場合は、普通の日本語で言い換えられる語を言い換える
- 送付後の記録は `/docs-tools:work-log` の定型 (作成 → 未送付、送付確認 → sent へ移動)
