# 作業ログの作成・追記

置き場: 引数で案件ディレクトリを受け取ったときは `<案件ディレクトリ>/docs/logs/work-log-YYYYMMDD.md`、
省略時はリポジトリ直下の `docs/logs/work-log-YYYYMMDD.md` (日付は当日)。当日ファイルが
既にあれば末尾に H2 節を追記し、なければ新規作成する。

## 書式

- 1 行目は `# 作業ログ YYYY-MM-DD`。H1 はこの 1 つだけ
- H2 は作業単位ごとに時系列順。見出しは体言止め (「〜の改稿」「〜への反映(N件)」
  「〜の確認」)。固定の節構成はなく、その日の作業数だけ並べる
- H3 は 1 つの H2 内に複数の下位項目があるときだけ使う
- 中身はすべて箇条書き。過去形の報告文 (「〜した」「〜を確認した」) で書き、
  段落文は使わない
- 依頼者の判断・承認はラベル付きで残す: 「依頼者の判断:」「依頼者の承認:」。指摘の言葉は
  引用せず、私が何をして何が誤りだったかを「経緯:」に事実で書く。ほかのラベルは「補足:」「対象:」
- ファイルパス・コミットハッシュ・短いコマンドはインラインコード。複数行の
  コマンドだけ bash コードブロックにし、置換箇所は `<...>` で示す。パスは相対表記。
  「根拠になった実行」の原文は例外で、1 行でもコードブロックにし、実行したとおりに書く
- 時刻 (HH:MM) は書かない。日付は「7月30日」のように文中に書く。「根拠になった実行」の日時と
  対象の時間範囲だけは、時刻とタイムゾーンまで書く

## 定型の記録

- ファイル変更: 対象パスと、新規作成か既存編集かを書く
- Notion 反映: 対象ページ → 直前に本文取得・一致確認 → 検索置換 N 箇所 (全文置換は
  不使用) → 再取得で確認、または再取得を省き「更新要求受理」として記録 →
  未対応の発見は「発見(未対応、依頼者の判断待ち):」で別出しする
- 送付ドラフト: 作成時は「`drafts/` 配下へ作成した。未送付」。送付確認後は
  「`archive/sent/` へ移動した」
- 根拠になった実行: 判断や文面の根拠にしたコマンド・クエリの実行を、1 回ごとに次の形 (項目と値の
  箇条書き) で書く。依頼者が実行して結果を会話に貼ったものも書く。原文が 20 行を超えるときは、
  原文をファイルに置いてパスを書く。認証情報と、個人を特定できる値 (利用者の ID・メールアドレス・
  IP アドレスなど) は書かない。原文に含まれるときは、その値だけを `<...>` に置き換える

````markdown
- 根拠になった実行: <何を確かめるための実行か>
  - 実行した人: <依頼者 / Claude / ほかの人の役割>
  - 日時: <10月27日 15:43 (JST)>
  - 場所: <実行した端末か画面>
  - 対象と範囲: <リソース>、<時間範囲 (タイムゾーンも書く)>
  - 結果の要点: <件数・値。0 件も書く>
  - 元の結果: <結果を置いたファイルのパス、または会話の記録のセッション ID と日時>
  ```<言語>
  <コマンドかクエリの原文>
  ```
````

- 実施していないことは、誤って完了扱いになり得る後続操作(コミット・Push・クラウド変更・
  送付)に限り、ログ末尾の「実施していないもの」節に1回でまとめる

## 手順

1. 当日の会話とツール実行の記録から、作業単位 (H2 相当) と、判断や文面の根拠にした実行 (依頼者が
   実行したものを含む) を抽出する。会話が要約されて手元にない実行は、`/docs-tools:session-recall` で
   記録を探す
2. 上記書式で本文を作り、Write する (既存ファイルへは末尾追記)
3. 報告には、対象パス、新規か追記かの別、追記した節の一覧を含める

## 記録の原則

- 事実のみを書く。推測は「(推測)」と明記する
- 完了と未完了を混ぜない。未実施・判断待ちはその旨を書く
- 週次サマリー (weekly-summary) は本 Skill の対象外 (書式は定義しない。作る場合は
  依頼者と書式を決めてから)
