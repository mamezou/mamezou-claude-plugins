# サブエージェントへの委任

本体(依頼者と話しているセッション)と担当(本体が起動するサブエージェント)の分け方、
依頼文に書くこと、返った結果の扱い。書き手は、下書きを任せた担当を指す。本体の会話には、
判断に要る結論と根拠の箇所だけを残す。

## 分け方

- 本体は、判断・確認・統合・依頼者への報告と、取り消しに手間のかかる操作を受け持つ。
  調べ・下書き・検査は、担当に任せることを既定にする
- 本体が直接するのは、即答できる質問、1〜2ファイルの小さな修正、1〜2資料を読む確認に限る
- 3資料以上を横断する調べは任せる。チャットやメールは、2件以上の投稿・スレッドを読む
  調べも任せる。「状況は?」への回答と指摘を受けた後でも、調べは同じ件数で分け、回答は
  本体が書く
- 任せた作業について本体が自分で資料を読むのは、任せる対象と完了条件を決めるための確認と、
  返った結果の採否を左右する根拠の確認に限る
- 質問に答えるための調べを任せることは、指示のないエージェントの起動に数えない
  (start-approval.md の「1応答1実行」の例外)。編集と下書きは、依頼者の指示を受けてから任せる
- 1つの担当で足りる作業を複数に分けない。並べて動かすのは、互いの結果を使わない作業に限る
- 本体は、担当が戻るたびに依頼者へ報告しない。本体が依頼者に知らせるのは、判断が要る
  とき、方針を変えたとき、成果物を見せられるときにする

## 担当に任せない操作

- メールやチャットの送信、下書きの作成など外部へ書き込むツールの呼び出し、ファイルや
  データの削除、コミットと push、`.claude/` の下(rules・設定・hook)の書き換え、クラウドと
  実機の変更は、依頼者の承認を受けた後も担当に渡さず、本体が行う
- 担当には、上の操作の対象の一覧と、コマンドか下書きの本文を作るところまでを任せる
- 下書きを任せる依頼文には、本文をファイルで返させ、外部へ書き込むツールを使わないことを書く

## 依頼文

- 担当は本体の会話を引き継がない。依頼文に、目的・成果物(既存への追記か新規か)・読者・
  対象と根拠の資料のパス・完了条件・返す形を書く
- 依頼者の言葉は、原文を日付とともに転記する。本体の案や解釈は「本体の案」と書いて、
  依頼者の言葉と分ける
- 正本(資料どうしが食い違ったときに従う資料)と、本体と担当の受け持ちを依頼文に書く。
  答えで成果物が変わる未決の点は、任せる前に依頼者に聞いて決める
- 返す形には、結論・根拠の箇所(パスと行)・確かめられなかった点を指定する。資料の全文や
  長い引用は返させない
- 書き方の指示は、規則の文を言い換えず、規則のファイルのパスと節の名前で渡す
- 書き手に「必ず入れる」を渡すときは、依頼者に見せて承認を受けた仕分け(必ず入れる・
  入れない・未確認)の言葉だけを写し、言葉を足さない
- 書き手への依頼に「未確認と明示せよ」と書かない。書き手が確かめられない点は、本文に
  書かせず、「確かめられなかった点」として返させる
- レビューの担当に挙げないよう頼んでよい点は、依頼者が会話で決めた点に限る。頼むときは、
  依頼者の発言の原文を添える
- 長文資料(設計書・手順書・共有ページ)の書き手には、資料の種類(検討資料か提案資料か)・
  書き手の立場(誰が提案する文として書くか)・文体(常体か敬体か)・資料の中での案の呼び名を
  渡す。依頼と記録から決まらない項目だけを、任せる前に依頼者に聞く
- 依頼者が「簡単に」「一言」「シンプルに」と頼んだ文面は、任せずに本体が下書きを書いて
  見せる。送付文面の下書きを任せるときは、承認を受けた仕分けと、実例のパスを渡す

## 返った結果の扱い

- 採る前に、採否を左右する根拠の箇所を本体が現物で確かめる。担当の結論を、そのまま
  依頼者へ転送しない
- 複数の担当の結果は、本体が1つにまとめて依頼者へ返す。レビューの指摘を採らなかった
  ときは、理由を添える
- 担当が書いた「未確認」「確認点」は、言葉のまま転送せず、本体が出典を開いて確かめる。
  確かめられない点は、答えで成果物が変わるなら、何が変わるか・選択肢・推奨を添えて
  依頼者に聞き、変わらないなら未確認として報告に1行で書く
- 担当が書いた原稿の直しは、1ファイルでも、書いた担当に戻す(同じエージェントを
  SendMessage で再開する)。本体が自分で直すのは、数値と事実の誤り、内部パスの除去、
  依頼者が原文で指定した置き換えに限る
- 依頼者の指摘が言い方(語・文体・体裁・呼び名)のときは、担当を増やさず、同じ担当に戻して
  最小の差分で直させる。別の担当に白紙から書き直させるのは、依頼者が指示したときに限る

## フックとの関係

- require-reading.sh は、`requireReading.rules[]` の target に当たるファイルの編集では、
  本体の会話の記録の末尾200行にある Read だけを数える。担当の Read、Skill のツールでの
  読み込み、Bash の cat は数えないため、本体が読んでいなければ担当の書き込みは止まる
- target に当たるファイルを担当に書かせるときは、本体が必読資料を Read してから任せる。
  担当の書き込みが止まったら(本体の Read が末尾200行から外れたときも止まる)、本体が
  もう一度 Read してから、担当に書き込みをやり直させる
- 担当に書かせるファイルは `.claude/` の外に置く。harness-change-check.sh は、`.claude/` の
  下の書き込みを、依頼者の最後の入力に承認の文字列(既定 `[harness-go]`)が無ければ止める。
  Agent の isolation: worktree は作業用の git worktree を `.claude/worktrees/` の下に作るため
  使わず、要るときは本体が `.claude/` の外に作ってパスを渡す

## モデル

- 調べ・横断検索・要約・検査・レビューを任せるときは model: sonnet を、下書きと複数資料の
  統合を任せるときは model: opus を指定する
- model を省かない。省くと、エージェントの定義にモデルが無い限り、本体と同じモデルで動く
- 案件の決まりが別のモデルを求める作業は、案件の決まりに従う
