# 文章ルール(送付文面の正本)

対象は先方・内部向けの送付文面。メール・チャット・Notion・資料を含み、ファイルとして
保存する文面と、下書きとしてツールへ渡す本文の両方に適用する。返信・チャット文面の文体の正本は Output Style
「Concise JA」(`/config` で Concise JA を選ぶ)。文の書き方・構成・言葉の禁止事項・
括弧と識別子・説明の量・成果物報告の型など返信向けの節は同 Style にある
(送付文面にも同じ基準を適用する)。出典は文化庁「公用文作成の考え方」と指摘の
記録。Stop hook (`response-quality.sh`)は機械化できる部分集合を検知する。

## 実例の確認

- 書く前に、依頼者が過去に送った同じ種類の文面を読む。同じ宛先の1件と、別の宛先の2件以上を
  目安にする。メールは送信済みのメールから、チャットは依頼者の過去の投稿から探す。添付
  ファイルは読まない。読んだ実例に、古い約束や誤りがあっても、今回の文面に持ち込まない
- 宛名・あいさつ・段落の分け方・見出し・箇条書き・結びは、読んだ実例の型に合わせる。
  言い回しは実例の文を使ってよい。事実・数・日付・約束は、今回の依頼と根拠資料から取る
- 書く前に、今回の依頼を「必ず入れる」「入れない」「未確認」に分ける。完成した稿と
  突き合わせて、依頼にない内容を足さず、依頼にある内容を消さない
- 言い方の指摘を受けたときは、内容を変えない。直したら変更前後を並べ、内容に差がない
  ことを示す。内容を変える提案は、文面とは別に出し、指示を待つ
- 下書きをツールへ渡すときは、検査した本文をそのまま渡す。下書きの依頼では、送信する
  ツールを使わない

## 語の選び方

語の選び方の表は Output Style「Concise JA」の「語の選び方」の1枚が正本。
送付文面にも同じ表を適用する。

## 指示語の置換確認

送付文面の指示語は1通あたり目安2回以下。判定基準は同 Style「指示語の置換確認」。
機械では判定できないため、件別の判定は書き手が行う。全廃への過補正はしない。

## 読者としての通し読み

grep と1文ごとの確認では、検査に通っても同じ形の短い文が並ぶ文章を見落とす。300字を超える
文書(送付文面・手順書・原稿・記事)は Write 確定前に、読み取り専用のサブエージェント
(model: sonnet)へ読者を名指しして頭から通して読ませ、つかえた箇所を挙げさせる。主語と述語の
対応も同じ依頼で見させる。返った指摘は本体が現物で確かめ、段落を単位に直す。文書では
1文60字を目安にとどめ、理由と動作は1文にまとめてよい。分けると同じ形の短い文が並ぶ
場合は分けない。段落は「読み手がこの段落を読んで次に何をするか」で組む。

## 送付文面

送付文面(ドラフト・Notion・exports 配下)の禁止項目(内部パス・ローカル拡張子・
組版記号・外部 AI 言及・禁止語)は `draft-precheck.sh` hook が編集時に検査する。案件の
禁止語は `.claude/harness.json` の `draftPrecheck.bannedTerms[]` に置く。検査項目は
`draftPrecheck.checks` で個別に止められる。

メールやチャットの下書きをツール(MCP)へ渡す呼び出しは、`draftPrecheck.toolRules[]` に
ツール名を書くと、同じ検査を通る。`requireReading.toolRules[]` に書き込むツールと読み取りの
ツールを書くと、書き込みの前に、読み取りのツールが少なくとも1回、正常に完了していることを
確認する。確認するのはこの1点だけで、実例の件数、宛先、本文まで読んだかは確認しない。それらは、
上の手順で行う。どちらの設定も、書くまでは何もしない。
